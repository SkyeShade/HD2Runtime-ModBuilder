# HD2Runtime ModBuilder application updates

This covers updates of the ModBuilder application itself. HD2Runtime SDK updates are separate; see "HD2Runtime SDK cache and updates" in the README.

## Release contract

The only update source is GitHub Releases of `SkyeShade/HD2Runtime-ModBuilder`, over HTTPS, without a token.

| | |
| --- | --- |
| Discovery | `GET https://api.github.com/repos/SkyeShade/HD2Runtime-ModBuilder/releases?per_page=20`, User-Agent `HD2Runtime-ModBuilder/<version>` |
| Release | Tag `v<x.y.z>` (stable semantic version). Drafts, prereleases and prerelease versions are ignored. `html_url` must be `https://github.com/SkyeShade/HD2Runtime-ModBuilder/releases/tag/v<x.y.z>`. |
| Package asset | `HD2Runtime-ModBuilder-v<x.y.z>-win-x64.zip` (at most 512 MB) |
| Manifest asset (1.0.1+) | `modbuilder-update-v2.json` (format 2, at most 64 KB) |
| Manifest asset (1.0.0) | `modbuilder-update.json` (format 1; read only by ModBuilder 1.0.0) |
| Checksum asset | `HD2Runtime-ModBuilder-v<x.y.z>-win-x64.zip.sha256` (for people; the app uses the manifest) |
| Download URLs | Exactly `https://github.com/SkyeShade/HD2Runtime-ModBuilder/releases/download/v<x.y.z>/<asset>`. Redirects may only go to `github.com`, `release-assets.githubusercontent.com` or `objects.githubusercontent.com` over HTTPS. |

ModBuilder 1.0.1 and later offer a release only if it has the package and `modbuilder-update-v2.json`. ModBuilder 1.0.0 needs the package and `modbuilder-update.json`. The newest qualifying release is compared with the running version; if it is not newer, nothing is shown.

### Manifests

Generated by `scripts/publish-windows.ps1`. `modbuilder-update-v2.json`:

```json
{
  "format": 2,
  "product": "HD2Runtime ModBuilder",
  "version": "1.4.3",
  "tag": "v1.4.3",
  "asset": "HD2Runtime-ModBuilder-v1.4.3-win-x64.zip",
  "size": 97870321,
  "sha256": "<64 lowercase hex>",
  "entrypoint": "HD2RuntimeModBuilder.exe",
  "updater": "HD2RuntimeModBuilder.Updater.exe",
  "commit": "<40 lowercase hex>"
}
```

`modbuilder-update.json` has the same fields with `"format": 1` and `"entrypoint": "HD2RuntimeGUI.exe"`: the exact form the 1.0.0 updater validates (it rejects any other format, entry point or extra property).

Unknown properties are rejected. `version`, `tag`, `asset` and `size` must match the release, and `entrypoint` and `updater` must be exactly those names (the manifest cannot point at other files). When GitHub publishes an asset `digest`, it must equal `sha256:<sha256>`.

### Package layout

The ZIP is the flat application folder, plus `modbuilder-files.json`:
- `HD2RuntimeModBuilder.exe`, `HD2RuntimeModBuilder.dll` and the rest of the `HD2RuntimeModBuilder.*` files;
- `HD2RuntimeModBuilder.Updater.exe`;
- everything else at the root.

```json
{ "format": 1, "product": "HD2Runtime ModBuilder", "version": "1.4.3",
  "files": [ { "path": "HD2RuntimeModBuilder.exe", "size": 123, "sha256": "<hex>" }, … ] }
```

The inventory lists every other file with its size and SHA-256. The installed copy of it tells the next updater which files belong to the app. Its format stays 1, which 1.0.0 also reads.

### Compatibility with 1.0.0 (`HD2RuntimeGUI.exe`)

ModBuilder 1.0.0 was `HD2RuntimeGUI.exe` / `HD2RuntimeGUI.dll`. Its in-app updater only accepts a package whose inventory contains `HD2RuntimeGUI.exe`. Every package therefore also contains **`HD2RuntimeGUI.exe`, a byte-identical copy of `HD2RuntimeModBuilder.exe`**. It is the same .NET launcher, so it starts the same app if run.

Updaters from 1.0.1 on never install this copy. When one updates a 1.0.0 installation:
- it moves every file the 1.0.0 inventory lists (`HD2RuntimeGUI.exe`, `.dll`, `.runtimeconfig.json`, `.deps.json`, `.staticwebassets.endpoints.json`, `HD2RuntimeGUI.Core.dll`, …) into the backup and does not restore them;
- it installs the `HD2RuntimeModBuilder.*` files;
- it writes an installed inventory without the compatibility copy;
- it deletes 1.0.0's WebView2 cache folder `HD2RuntimeGUI.exe.WebView2` (the app keeps no data in browser storage);
- it starts `HD2RuntimeModBuilder.exe`.

Files the user put in the folder, including ones named `HD2RuntimeGUI.*`, are not in the inventory and are left alone. If replacement fails, the 1.0.0 files come back and `HD2RuntimeGUI.exe` is restarted.

Keep shipping the compatibility copy and the format-1 manifest for as long as 1.0.0 installations should be able to update themselves. Without them, 1.0.0 reports that the update is invalid and its users must download manually.

## Flow

1. **Check.** At startup and then every 10 minutes while the app runs, in the background. A background check keeps the current banner visible while it runs; if it fails, the last known result stays. Offline, rate-limited, malformed or failed checks are silent (the status appears in Settings → Application updates). Settings has **Check for updates**, which always queries GitHub.
2. **Banner.** A newer version shows a banner under the titlebar with **Install update**, **View release notes** (the official release page, opened in the browser) and **Dismiss**. Dismissing hides that version (persisted in `%LOCALAPPDATA%\HD2RuntimeGUI\app-update.json`); a newer release shows the banner again.
3. **Install** (in the app, `AppUpdateService`):
   - Only a release installation (one with `modbuilder-files.json`) updates itself. A development build, or a folder the user cannot write to, gets **Open release page** instead.
   - Download the manifest and validate it.
   - Download the ZIP to `%TEMP%\HD2Runtime-ModBuilder-Update\<version>\` with the exact size.
   - Verify the size and SHA-256 against the manifest.
   - Extract to `…\staged\`. Rooted, `..`, drive-qualified, duplicate, link and reserved (`.modbuilder-update-backup`) entries are rejected. The ZIP must contain exactly the inventory's files, each with its recorded size and SHA-256, and include the entry point and the updater.
   - Start `staged\HD2RuntimeModBuilder.Updater.exe --pid --started --install --staged --version --result`, then quit.
   - Any failure before this point keeps the app running, removes the temporary files and shows the error in the banner.
4. **Replace** (the new release's updater, running from the staged copy, so nothing in the installation folder is locked by it):
   - Wait for the app's process to exit. The process ID is checked together with its start time.
   - Re-check the staged inventory and files.
   - Move the installed app's files into `<install>\.modbuilder-update-backup\`: the old inventory's files, plus any path the new package writes.
   - Copy the new files in (not the compatibility copy), then write the installed inventory.
   - Retry locked files briefly.
   - On any failure: delete what was copied, move the backup back and restart the old version (`HD2RuntimeModBuilder.exe`, or `HD2RuntimeGUI.exe` for a restored 1.0.0).
   - On success: delete the backup, stale directories and, when migrating from 1.0.0, its WebView2 cache; then start `HD2RuntimeModBuilder.exe`.
   - Files in the folder that are not part of the app are never touched.
5. **Next start.** The updater writes `%LOCALAPPDATA%\HD2RuntimeGUI\app-update-result.json`. The app shows the result once (for example "HD2Runtime ModBuilder was updated to 1.4.3." or the failure reason), deletes the file, and after a success removes the staging folder and any leftover backup.

The updater is a separate self-contained, trimmed, single-file executable (about 11 MB) with no dependency on the MAUI app or an installed .NET. It is the new release's own updater, verified as part of the package, and it runs outside the installation folder. No administrator rights are requested. User data in `%LOCALAPPDATA%\HD2RuntimeGUI\` (projects, exports, SDK cache, imported icons, preferences) is outside the application folder and is never part of an update.

## Publishing a release

1. Set `Hd2RuntimeGuiVersion` in `Directory.Build.props`, add `docs/release-notes/v<x.y.z>.md`, and commit.
2. Run `./scripts/publish-windows.ps1` on the clean tree. It fails on:
   - uncommitted changes, wrong metadata or a non-reticle icon;
   - leftover `HD2RuntimeGUI.*` files, or a compatibility copy that differs from the entry point;
   - unexpected files, or manifests that do not match the ZIP.
3. Optionally run `tools/update-from-1.0.0.ps1`. It installs the published 1.0.0 in a sandbox, runs the 1.0.0 in-app update code against the new artifacts, and lets the new updater migrate and restart the app.
4. Create the GitHub release with tag `v<x.y.z>` on `SkyeShade/HD2Runtime-ModBuilder` (not a draft or prerelease). Use the release notes as the description and upload the four files from `artifacts/release/`: the ZIP, `modbuilder-update-v2.json`, `modbuilder-update.json` and the `.sha256`.
5. Do not replace assets of a published release. Publish a new version instead; running apps pick up a new release within 10 minutes.
